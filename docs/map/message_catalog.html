CRISalid Bus – Exchange Map & Message Catalog

This page documents the CRISalid message bus, with a global view of exchanges and queues, followed by detailed documentation for each exchange and its messages.

🌐 Global Map of Exchanges and Queues

CRISalid currently relies on several RabbitMQ exchanges to make its services communicate asynchronously.

In crisalid-bus, all exchanges are of type topic and use an “at-least-once” delivery strategy, which means that messages may be delivered more than once in case of failure, and consumers must be designed to handle potential duplicates and be idempotent. Consumers, in turn, must be able to handle the possibility of missing messages (e.g., by carefully processing “unchanged” events or implementing reconciliation mechanisms).

Messages are primarily of two types: events and tasks.

  • Events represent occurrences or changes in the system (e.g., “a person was created”, “a publication was harvested”). They are typically not acknowledged (i.e., they are fire-and-forget).
  • Tasks represent work that needs to be done (e.g., “harvest this publication”). They may be acknowledged (i.e., the producer expects a confirmation that the task was received and will be processed).

🔀 Routing key convention — interactive vs batch

All queues in the CRISalid bus will progressively be split into two queues suffixed -interactive and -batch. When a queue has been split, every message routed to it gains a 5th routing key segment: .interactive or .batch.

  • .interactive — message triggered by a real-time user action (e.g. a user requesting a document harvest, an operator editing a person record). Processing must be fast and must not be starved by bulk loads.
  • .batch — message produced by an ETL pipeline or mass-import job. Processing can tolerate higher latency.

Each split queue has its own channel and prefetch count, its own semaphore, and its own dead-letter queue on the exchange-specific dead-letter exchange (dlx.graph for graph-exchange queues, dlx.publications for publications-exchange queues, dlx.directory for directory-exchange queues) so failures in one traffic class do not affect the other.

Additional considerations
  • A research structure must have a generic type and at least one type or local type.
  • Relationships of type “member_of” can have a subtype only when characterizing the supervision of a research unit. Inclusion relationships (“part_of”) do not have subtypes.
  • The targets of relationships must be the tracking ids of structures already created in previous messages, except for external institutions that you do not manage: in this case, simply indicate “uai-1234” or “ror-ABCD” according to the type of identifier you have for the external institution.
  • For details on typologies, see the CRISalid Wiki: https://www.esup-portail.org/wiki/spaces/ESUPCRISalid/pages/1673035787/Import+des+donn%C3%A9es+structures+v2

  • Either display_name or at least one entry in names must be provided. If display_name is absent, it is computed automatically from the first available name.

Queues: sovisuplus-interactive and sovisuplus-batch

Overview

sovisuplus subscribes to two queues on the graph exchange. Both queues are asserted by sovisuplus at startup — no manual pre-creation is required, but the dlx.graph dead-letter exchange must exist beforehand (it is declared in definitions.sample.json).

Queue Binding keys Prefetch Env var
sovisuplus-interactive event.*.*.*.interactive 5 AMQP_INTERACTIVE_QUEUE_NAME
sovisuplus-batch event.*.*.*.batch 20 AMQP_BATCH_QUEUE_NAME

Published by crisalid-ikg after processing a registered user action (a task.documents.document.* message persisted as a Change node). They close the feedback loop: sovisuplus can unfreeze the frozen data, notify the user, and display per-item warnings. Emitted only in interactive mode — batch replays of stored changes after a document recompute stay silent (the outcome is still recorded on the Change node in the graph).

  • applied — the action was applied. A non-empty warnings array signals a partial success: some items were skipped or degraded (e.g. a contributor that could not be resolved). On success sovisuplus receives this event and the usual event.documents.document.updated.interactive.
  • failed — the action was not applied; error_message carries the cause. Also emitted when the inbound task message cannot be validated into a Change (correlation fields are then copied from the raw payload) or when the target document does not exist. No document event follows a failure.
{
  "type": "change",
  "event": "applied|failed",
  "fields": {
    "uid": "sovisuplus:<id>",
    "id": "<uuid>",
    "application": "sovisuplus",
    "person_uid": "<uid of the user who performed the action>",
    "target_type": "DOCUMENT",
    "target_uid": "<string>",
    "path": "<string|null>",

Outbound messages (sovisuplus → crisalid-ikg-actions-interactive)

sovisuplus publishes task messages to the graph exchange with routing keys of the form task.<domain>.<entity>.<action>.interactive. All outbound messages from sovisuplus carry the .interactive suffix — batch task publishing is not implemented.

The queue crisalid-ikg-actions-interactive is bound to receive all task.*.*.*.interactive keys.

{
  "uid": "sovisuplus:<id>",
  "id": "<uuid>",
  "actionType": "ADD|REMOVE|UPDATE|FETCH|MERGE",
  "targetType": "DOCUMENT|PERSON|HARVESTING",
  "targetUid": "<string>",
  "path": "<string|null>",
  "parameters": { ... },
  "timestamp": "<ISO datetime>",
  "personUid": "<string>",
  "application": "sovisuplus"
}

actionType and targetType are Prisma enum values serialized as uppercase strings. uid is the globally-unique message id (<application>:<id>) under which crisalid-ikg persists the action as a Change node; path selects the sub-resource the action targets (e.g. contributions, subjects).

actionType targetType path Routing key
MERGE DOCUMENT — task.documents.document.merge.interactive
REMOVE DOCUMENT — task.documents.document.remove.interactive
ADD DOCUMENT — task.documents.document.add.interactive
UPDATE DOCUMENT contributions task.documents.document.update.interactive
UPDATE PERSON — task.people.person.update.interactive
FETCH HARVESTING — task.people.documents.fetch.interactive

Contribution update task (UPDATE / DOCUMENT / path = contributions)

Routing key: task.documents.document.update.interactive

Emitted when a user saves the Authors tab of a document in sovisuplus. The message carries the complete, authoritative contributor list for the document. crisalid-ikg applies replace semantics: contributors present in the list are created/updated, contributors absent are removed, and an empty list removes all of them. The action is persisted as a Change and replayed after every recompute from source records, so a saved list pins the document against later harvests (newly-harvested co-authors do not reappear until the user saves again).

Payload

parameters.contributions is the full, ordered contributor list. Each entry carries a person, its roles (Library of Congress relator URIs), an optional rank, and its affiliations.

Additional considerations
  • person.uid may be an internal uid (local-<id>), an external uid (orcid-…, idref-…, …), or null for a brand-new external contributor to be created from displayName. When a uid is given but not found, the person is matched by its identifiers, falling back to creation.
  • Internal persons (external: false): incoming identifiers and names are frozen (ignored); only the contribution itself and its affiliations are updated.
  • External persons (external: true): consistent incoming identifiers are added; identifiers that already belong to a different person are discarded.
  • affiliations are HAL-sourced (the sovisuplus author selector autocompletes against HAL), so each normally carries the HAL structId plus any of idref/ror/isni/nns/wikidata. They are resolved in memory to AuthorityOrganization nodes — no source-layer node is persisted.
  • roles are LoC relator URIs (…/aut author, …/ctb contributor, …/edt editor, …).
  • When several contribution-update changes accumulate on a document, only the latest is applied on replay; older ones are preserved for the forthcoming modification-history feature.
  • Identifiers with an unknown type or a value that does not match the type-specific pattern (e.g. an idhals made of digits) are dropped before any write and reported with an INVALID_IDENTIFIER warning on the outcome event.
  • Safety guard: if the submitted list is non-empty but none of its contributions can be applied, the change fails (previous contributors are kept) instead of wiping the contributor list. An intentionally empty list still removes all contributors.
  • The outcome (success, partial success with warnings, or failure) is reported back on event.changes.change.<applied|failed>.interactive — see Change events.
